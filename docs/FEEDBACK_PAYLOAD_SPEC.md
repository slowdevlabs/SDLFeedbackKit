SDLFeedbackKit — Feedback Payload Specification
1. Document Purpose
이 문서는 SDLFeedbackKit에서 생성되는 FeedbackPayload의 데이터 구조, 필드 의미, 유효성 규칙, Attachment 표현 방식, Metadata 정책, 식별자 및 시간 정보 처리 원칙을 정의한다.
이 문서의 목표는 다음과 같다.
	•	Client와 Backend 사이의 데이터 계약을 명확히 한다.
	•	Transport 구현체가 동일한 의미의 데이터를 일관되게 다룰 수 있도록 한다.
	•	Server-side validation 기준을 제공한다.
	•	Payload 확장 시 하위 호환성을 유지할 수 있는 원칙을 정한다.
	•	Self-hosted Backend 구현자가 안전하게 Feedback 데이터를 처리할 수 있도록 한다.
이 문서는 특정 HTTP 형식이나 특정 Backend Provider를 강제하지 않는다.

이 Specification이 정의하는 범위:

이 영역은 각 Transport 및 Backend 구현의 책임이다.

FeedbackPayload는 다음 두 종류의 정보를 결합한다.
User-provided data
+
Automatically collected technical context
예:
User-provided
──────────────────

Message

Automatic / Host Context
────────────────────────
Client ID
App ID

Payload의 목적은 사용자의 의견 내용뿐 아니라 문제 재현과 앱 식별에 필요한 최소한의 기술 Context를 함께 전달하는 것이다.

6. clientID
6.1 Purpose
clientID는 Feedback Submission을 Client 측에서 식별하기 위한 UUID다.
예:
2E4199E2-907A-47C1-98CE-BC23EEA96C21

6.2 Generation
SDLFeedbackKit이 Feedback 전송 단위마다 생성한다.
권장:
UUID()

6.3 Stability
동일 Submission을 재시도하는 동안에는 가능하면 동일한 clientID를 유지한다.
즉:
Submit attempt 1
→ clientID A

Network failure

Retry
→ clientID A
새로운 Feedback Form Submission을 시작한 경우에는 새로운 ID를 생성한다.

6.4 Purpose on Backend
Backend는 필요에 따라 clientID를 다음 용도로 활용할 수 있다.
Duplicate detection
Idempotency
Log correlation
Attachment correlation
Support investigation
단, Backend가 clientID를 신뢰 가능한 인증 식별자로 사용해서는 안 된다.

7. Server ID
clientID와 Backend가 생성하는 Server-side ID는 별개의 개념이다.
예:
clientID
────────────────────
UUID generated by SDK

serverID
────────────────────
Canonical ID generated by backend
Backend가 Server ID를 생성하는 것을 권장한다.
예:
fb_01JABCXYZ...
또는 자체 UUID.

8. appID
8.1 Purpose
Feedback이 어느 앱에서 발생했는지 안정적으로 구분하기 위한 Host-defined identifier다.
예:
doligo
timetape
symbolicdrop
swipe-flags

8.2 Requirements
appID는:
	•	비어 있으면 안 된다.
	•	앱 이름과 독립적이어야 한다.
	•	가능한 한 출시 이후 변경하지 않는다.
	•	Backend에서 partition/filter key로 사용 가능해야 한다.

8.3 Recommended Format
권장 문자:
a-z
0-9
-
_
.
예:
doligo
time-tape
com.example.app
엄격한 형식을 Package가 강제할 필요는 없지만 Backend-friendly identifier를 권장한다.

8.4 Length
권장 최대:
128 characters
Backend는 별도 Validation을 수행해야 한다.

9. appName
9.1 Purpose
사람이 읽을 수 있는 앱 표시 이름이다.
예:
돌리GO
TimeTape
SymbolicDrop

9.2 Stability
appName은 변경될 수 있다.
따라서 Backend에서 앱을 식별하는 Primary Key로 사용해서는 안 된다.
식별은 appID를 사용한다.

9.3 Length
권장 최대:
200 characters

10. appVersion
10.1 Source
일반적으로 Host Bundle의:
CFBundleShortVersionString
에서 얻는다.

10.2 Example
1.3.0
2.0
0.9.4

10.3 Optionality
값을 읽을 수 없는 경우:
nil
을 허용한다.
Package는 임의로 "unknown" 문자열을 삽입하지 않는 것을 권장한다.

11. buildNumber
11.1 Source
일반적으로:
CFBundleVersion
에서 얻는다.

11.2 Example
42
20260808
137

11.3 Type
String으로 유지한다.
이유:
Build Number는 숫자처럼 보일 수 있지만 플랫폼과 개발 정책에 따라 문자열로 다루는 편이 안전하다.

12. platform
12.1 Type
public enum FeedbackPlatform: String {
    case iOS
    case macOS
}

12.2 Purpose
현재 Feedback이 발생한 플랫폼을 명시한다.

12.3 Serialized Recommendation
외부 표현에서는 안정적인 lowercase identifier를 사용하는 것을 권장한다.
예:
"platform": "ios"
"platform": "macos"
Swift Enum의 Case Naming과 wire-format identifier를 반드시 동일하게 유지할 필요는 없다.

13. osVersion
13.1 Purpose
문제 재현에 필요한 OS Version을 전달한다.
예:
26.0
26.1
15.7.3

13.2 Requirements
가능한 경우 항상 제공한다.
Package가 지원되는 Apple 플랫폼에서 실행 중이라면 필수값으로 취급한다.

13.3 Do Not Parse Semantically
Backend는 반드시 이 값을 숫자나 Decimal로 해석할 필요가 없다.
권장:
String

14. localeIdentifier
14.1 Purpose
사용자가 사용하는 Locale Context를 제공한다.
예:
ko_KR
en_US
es_ES
또는 Foundation이 반환하는 표준 식별자.

14.2 Use Cases
Localization issue investigation
Language-specific UI issue
Formatting issue
Regional behavior differences

14.3 Optionality
값을 얻을 수 없는 경우 nil을 허용한다.

15. category
15.1 Type
public struct FeedbackCategory {
    public let id: String
    public let title: String
}

15.2 Purpose
사용자가 선택한 Feedback 종류를 나타낸다.
예:
id: bug
title: Bug Report

15.3 Category ID
Backend에서 분류에 사용할 안정적 식별자다.
예:
general
bug
feature_request
other
translation
content_issue

15.4 Category Title
사람이 읽을 수 있는 표시 문자열이다.
Localized될 수 있다.
예:
버그 신고
Bug Report
Informe de error
Backend는 분류 로직에 title보다 id를 사용하는 것을 권장한다.

15.5 Length Limits
권장:
category.id
Maximum 64 characters

category.title
Maximum 200 characters

16. message
16.1 Purpose
Feedback의 핵심 사용자 입력이다.

16.2 Required
Default Configuration에서는 필수다.
isRequired = true

16.3 Default Limits
권장:
Minimum
1 character

Maximum
5,000 characters

16.4 Whitespace Handling
Validation 전:
Leading/trailing whitespace only
입력은 Empty로 간주할 수 있다.
예:
"      "
는 유효한 Message가 아니다.
다만 실제 저장 시 사용자의 본문 Formatting을 불필요하게 변경하지 않는다.

16.5 Normalization
Package는 과도한 Text Normalization을 하지 않는다.
예:
	•	줄바꿈 유지
	•	Emoji 유지
	•	Unicode 유지
	•	사용자 문장 부호 유지
HTML sanitization은 Package 책임이 아니다.
Backend나 Dashboard가 HTML을 렌더링한다면 별도의 Escape가 필요하다.

17. email
17.1 Purpose
사용자가 회신을 원할 경우 선택적으로 제공하는 연락용 Email이다.

17.2 Default
Enabled
Optional

17.3 Maximum Length
권장:
320 characters

17.4 Client Validation
Client에서는 기본적인 형식 오류만 방지한다.
SDLFeedbackKit은 완벽한 RFC Email Validator를 목표로 하지 않는다.

17.5 Empty Value
입력되지 않은 경우:
nil
을 사용한다.
다음 형태는 피한다.
""
"null"
"N/A"

17.6 Privacy
Email은 사용자가 명시적으로 입력한 경우에만 Payload에 포함한다.
자동으로 Apple ID나 시스템 계정 주소를 수집하지 않는다.

18. metadata
18.1 Purpose
특정 앱에서 Feedback 조사에 필요한 추가 Context를 전달한다.
예:
[
    "screen": "destination",
    "datasetVersion": "1.4.0",
    "mode": "stay"
]

19. Metadata Type
MVP에서는 다음 타입만 허용한다.
[String: String]

20. Unsupported Metadata Types
MVP에서는 다음을 지원하지 않는다.
Nested Dictionary
Array
Boolean
Integer
Double
Date
Binary Data
Arbitrary JSON
필요하면 개발자가 String으로 명시적으로 변환한다.
예:
[
    "isPremium": "true",
    "itemCount": "12"
]

21. Metadata Limits
권장 기본 제한:
Maximum entries
32

Maximum key length
64 characters

Maximum value length
1,000 characters

22. Metadata Total Size
개별 필드 제한 외에 전체 Metadata size도 Backend에서 제한하는 것을 권장한다.
권장 초기 상한:
32 KB serialized size
정확한 wire serialization에 따라 실제 크기는 달라질 수 있다.

23. Metadata Key Naming
권장:
camelCase
snake_case
dot.notation
중 하나를 프로젝트에서 일관되게 사용한다.
SDLFeedbackKit 자체는 특정 Naming Convention을 강제하지 않는다.

24. Reserved Metadata Keys
System Field와의 충돌을 방지하기 위해 다음 이름은 Metadata에서 사용하지 않는 것을 권장한다.
clientID
appID
appName
appVersion
buildNumber
platform
osVersion
localeIdentifier
category
message
email
attachment
createdAt
Package 내부 Payload 구조상 충돌은 발생하지 않지만 Backend flattening 과정에서 혼란이 생길 수 있다.

25. Metadata Trust
Backend는 Metadata를 신뢰하면 안 된다.
예를 들어:
metadata["isPremium"] = "true"
라고 전달되었다고 해서 실제 결제 상태라고 가정해서는 안 된다.
Metadata는 디버깅 Context다.
권한 판단이나 인증에는 사용하지 않는다.

26. attachment
26.1 Type
FeedbackAttachment?

26.2 Default
Attachment는 선택 사항이다.
nil
을 허용한다.

27. FeedbackAttachment Model
개념 구조:
public struct FeedbackAttachment: Sendable {

    public let data: Data
    public let filename: String
    public let mimeType: String

    public let pixelWidth: Int?
    public let pixelHeight: Int?

    public let byteCount: Int
}

28. Attachment Count
MVP에서는:
Maximum 1 attachment
이다.
Payload는 배열이 아닌 단일 Optional Attachment를 사용한다.

29. Attachment Source
초기 Attachment는 이미지에 한정한다.
예:
Screenshot
Photo
Image file
다음은 MVP 범위 밖이다.
Video
Audio
ZIP
Log file
PDF
Text file
Multiple files

30. Image Processing
Transport에 전달되기 전에 SDLFeedbackKit이 이미지를 최적화한다.
Pipeline:
Source image
    ↓
Decode
    ↓
Normalize orientation
    ↓
Resize
    ↓
Re-encode
    ↓
Metadata removal
    ↓
Byte size validation
    ↓
FeedbackAttachment

31. Attachment Original Data
원본 이미지 데이터를 그대로 Payload에 전달하는 것을 기본으로 하지 않는다.
목표:
	•	대역폭 감소
	•	메모리 감소
	•	개인정보 Metadata 제거
	•	Backend 저장 비용 감소

32. Maximum Image Dimension
Default 권장값:
1,800 px
긴 변 기준이다.
예:
4032 × 3024
→
1800 × 1350
원본이 제한보다 작은 경우 Up-scaling하지 않는다.

33. Maximum Attachment Bytes
Default 권장:
1,000,000 bytes
약 1 MB.
이는 최적화 이후 최종 Attachment 데이터 기준이다.

34. Compression Quality
초기 기본값:
0.8
정확한 의미는 사용되는 encoder에 따라 다를 수 있다.

35. Attachment Encoding
MVP 기본 포맷으로 JPEG를 우선 고려한다.
예:
mimeType
image/jpeg
단, 최종 Attachment Encoding 정책은 ATTACHMENT_SPEC.md에서 더 구체적으로 정의한다.

36. filename
36.1 Purpose
Transport 및 Backend에서 Content-Disposition 또는 파일 식별에 사용할 수 있는 사용자 친화적 파일 이름이다.

36.2 Security
Backend는 Client가 전달한 filename을 Storage Object Key로 그대로 사용해서는 안 된다.
예:
Client filename
feedback.jpg

Server storage key
attachments/01J.../image.jpg
Server가 자체 Key를 생성한다.

36.3 Recommended Client Filename
예:
feedback.jpg
feedback-2E4199E2.jpg
민감한 로컬 파일 경로나 사용자 이름을 포함해서는 안 된다.

37. mimeType
Transport가 Attachment를 적절한 Content Type으로 전송할 수 있도록 한다.
예:
image/jpeg
image/png
image/heic
Backend는 실제 Binary Signature와 Content Type을 별도로 검증해야 한다.
Client의 mimeType만 신뢰하면 안 된다.

38. byteCount
data.count와 일치해야 한다.
불일치 시 Package 내부 버그로 간주한다.
개념적으로:
byteCount == data.count

39. pixelWidth / pixelHeight
이미지 차원을 전달한다.
예:
pixelWidth: 1800
pixelHeight: 1170
알 수 없는 경우 nil을 허용한다.
Backend는 이를 Security Validation의 유일한 근거로 사용하지 않는다.

40. createdAt
40.1 Purpose
Client에서 Feedback Submission Payload가 생성된 시간을 나타낸다.

40.2 Type
Date

40.3 Generation
Payload 생성 시점에 SDLFeedbackKit이 설정한다.

40.4 Retry
동일 Payload Retry에서는 기존 createdAt을 유지하는 것을 권장한다.
즉:
Feedback created
10:00:00

Retry
10:00:15

createdAt
10:00:00

41. Server Timestamp
Backend는 별도로 Server timestamp를 기록해야 한다.
예:
created_at_client
created_at_server
Client clock은 신뢰할 수 없기 때문이다.
Server-side canonical ordering에는 Server timestamp를 사용하는 것을 권장한다.

42. Date Serialization
Transport가 JSON 등으로 직렬화하는 경우 권장 형식:
ISO 8601 UTC
예:
2026-08-08T02:14:37Z
밀리초 포함 여부는 Backend Contract에서 일관되게 결정한다.

{

44. Attachment Serialization Strategies
SDLFeedbackKit은 다음 방식 중 어느 것도 강제하지 않는다.
Strategy A — Multipart
multipart/form-data

metadata JSON
+
image binary

Strategy B — Two-step Upload
1. Attachment upload
2. Feedback JSON containing attachment reference

Strategy C — Presigned Upload
1. Request upload URL
2. Upload attachment
3. Submit Feedback metadata

Strategy D — Base64 JSON
기술적으로 가능하지만 대형 이미지에서는 권장하지 않는다.
이유:
	•	약 33% 크기 증가
	•	메모리 사용량 증가
	•	Payload 비효율

45. Recommended HTTP Representation
Reference Backend를 만든다면 MVP에서는 Multipart 방식이 가장 단순하다.
개념:
POST /v1/feedback

Part:
payload
Content-Type: application/json

Part:
attachment
Content-Type: image/jpeg
그러나 이는 SDLFeedbackKit Core Contract가 아니다.

46. Nullability Policy
Optional 값이 없는 경우 Transport는 Backend contract에 따라:
omit field
또는:
"email": null
을 선택할 수 있다.
다만 빈 문자열로 대체하지 않는 것을 권장한다.

47. Empty String Policy
다음 필드는 Empty String을 유효한 값으로 취급하지 않는다.
appID
appName
category.id
category.title
message when required
Optional field가 비어 있다면 nil로 정규화하는 것을 권장한다.
예:
email = ""
→ nil

48. Unicode Policy
모든 String Field는 Unicode를 지원한다.
예:
한글
日本語
Español
Emoji 🎉
Arabic
Accented characters
Backend 역시 UTF-8을 기준으로 처리하는 것을 권장한다.

49. Character Count vs Byte Count
Text field 제한은 사용자 경험 측면에서는 Character Count를 기준으로 할 수 있다.
Backend는 추가로 Byte Size 제한을 적용해야 한다.
Unicode는 character count와 UTF-8 byte count가 다를 수 있기 때문이다.

50. Recommended Request Size Limit
Backend Reference 구현에서는 전체 Request 크기에 명시적인 상한을 두는 것을 권장한다.
초기 권장:
2 MB ~ 3 MB
이 범위는:
1 MB attachment
+
text metadata
+
multipart overhead
를 고려한 값이다.
정확한 값은 Backend 구현에서 결정한다.

8. Transport submission

56. Attachment Privacy
이미지는 사용자가 명시적으로 선택한 경우에만 포함한다.
Package는 사용자가 선택하지 않은 Screenshot 또는 화면 정보를 자동 첨부하지 않는다.
Automatic Screenshot Capture는 MVP 범위 밖이다.

57. Metadata Privacy Responsibility
Custom Metadata는 Host App이 제공하므로 개발자는 민감정보를 넣지 않도록 주의해야 한다.
피해야 할 예:
metadata: [
    "password": "...",
    "authToken": "...",
    "fullAddress": "..."
]
README 및 Integration Guide에서 이를 명확하게 경고한다.

58. Stable Fields
다음 필드는 향후에도 Core Payload 의미를 유지하는 것을 목표로 한다.
clientID
appID
appName
category
message
email
metadata
attachment
createdAt

59. Additive Evolution
새로운 Payload Field는 가능하면 Optional로 추가한다.
예:
public let deviceModel: String?
이러한 방식은 기존 Transport 구현과 Backend 호환성을 유지하기 쉽다.

60. Removing Fields
Public FeedbackPayload에서 기존 필드를 삭제하거나 의미를 바꾸는 것은 Breaking Change로 간주한다.
v1.0 이후에는 Major Version 변경이 필요하다.

61. Enum Evolution
FeedbackPlatform 같은 Enum의 새로운 Case 추가는 외부 코드의 exhaustive switch에 영향을 줄 수 있다.
따라서 향후 플랫폼 확장을 고려해 API 설계 시 주의한다.

62. Transport Compatibility
Transport 구현자는 알 수 없는 미래 필드가 추가되더라도 가능한 한 기존 전송 흐름이 깨지지 않도록 설계하는 것이 좋다.
Backend JSON Parser 또한 unknown field를 무시할 수 있는 구조를 권장한다.

63. Payload Schema Version
MVP에서는 Payload 내부에 별도:
schemaVersion
필드를 넣지 않는 것을 우선 권장한다.
이유:
SDLFeedbackKit Core Payload와 실제 wire serialization은 동일한 개념이 아니기 때문이다.
Backend Transport가 자체 API Schema Version이 필요하다면 다음과 같이 관리할 수 있다.
POST /v1/feedback
또는 wire-format 안에서 별도 version 필드를 사용할 수 있다.
향후 공식 Reference Backend Contract가 생길 경우 재검토한다.

64. Idempotency Guidance
Backend에서 중복 Submit을 방지하고 싶다면:
appID + clientID
조합을 Idempotency Key 후보로 사용할 수 있다.
예:
UNIQUE(app_id, client_id)
하지만 이는 Reference Backend 구현 선택이며 SDLFeedbackKit에서 강제하지 않는다.

65. Attachment Correlation
Backend가 Attachment와 Feedback Row를 연결할 때 Client filename 대신 Server-side identifier를 사용한다.
권장:
Feedback server ID
↓
Generated attachment key
↓
R2 / S3
예:
feedback/fb_01JABCXYZ/attachment.jpg

66. Database Storage Guidance
개념적 저장 예:
id

app_version
build_number
platform
os_version
locale
category_id
category_title

attachment_key
created_at_client
created_at_server
이는 SDLFeedbackKit에서 요구하는 DB Schema가 아니라 Reference 구현 지침이다.

67. Metadata Storage
D1, PostgreSQL 등에서 Metadata는 JSON Text 또는 JSON-compatible column으로 저장할 수 있다.
예:
{
  "screen": "result",
  "mode": "stay"
}
Backend는 가능한 한 Metadata를 다시 임의의 DB Column으로 flatten하지 않는 것을 권장한다.
앱마다 Key가 다르기 때문이다.

68. Attachment Storage
Binary Attachment를 D1 같은 relational database에 직접 저장하는 것은 권장하지 않는다.
권장:
D1
→ Feedback metadata

R2
→ Attachment binary
D1에는:
attachment_key
mime_type
byte_count
width
height
등의 reference 정보만 기록한다.

69. Failure Before Transport
다음 경우 Payload는 Transport에 전달되지 않는다.
Invalid required message
Invalid required email
Metadata limit exceeded
Attachment processing failed
Attachment size exceeded
Invalid category

70. Failure During Transport
Transport가 실패하면 동일 Payload를 사용자 Retry에 재사용할 수 있다.
이 경우 가능한 한 다음 값을 유지한다.
clientID
createdAt
message
metadata
attachment

71. Form Edit After Failure
전송 실패 후 사용자가 내용을 수정한다면 새로운 Payload를 생성할 수 있다.
권장 정책:
User edits content
→ new logical submission
→ new clientID
다만 정확한 UX 구현은 Form Model 설계에 따라 달라질 수 있다.

72. Client-generated Fields Integrity
SDLFeedbackKit 내부에서는 다음 invariant를 유지한다.
clientID is non-empty UUID

appID trimmed value is non-empty

appName trimmed value is non-empty

category.id is non-empty

category.title is non-empty

byteCount == attachment.data.count

message respects configured limits

metadata respects package limits

73. Logging
Package나 Transport가 Debug Logging을 제공할 경우 다음 데이터를 기본적으로 로그에 그대로 출력하지 않는 것을 권장한다.
Message body
Email
Attachment binary
Potentially sensitive metadata
개발자가 명시적으로 Debug를 활성화한 경우에도 개인정보 노출에 주의한다.

74. Description / Debug String
FeedbackPayload에 CustomStringConvertible을 구현한다면 민감값을 Redact해야 한다.

  category: bug,

권장하지 않는 출력:
message: "사용자의 전체 메시지..."

80. Final Payload Contract
SDLFeedbackKit의 Payload는 다음 원칙으로 정의한다.
A feedback payload is an immutable client-generated snapshot containing user feedback, minimal app/environment context, optional developer metadata, and at most one optimized image attachment.
다시 말해:
FeedbackPayload
=
Stable Client ID
+
App Identity
+
Environment Context
+
Feedback Category
+
User Message
+
Optional Email
+
Custom Metadata
+
Optional Optimized Image
+
Client Timestamp
SDLFeedbackKit은 여기까지 책임지고,
Serialization
Network
Authentication
Storage
Validation
Abuse Prevention
은 Transport와 Self-hosted Backend의 책임으로 남긴다.

81. Architectural Rule
새로운 Payload Field를 추가하기 전 다음 질문을 확인한다.
이 정보가 일반적인 iOS/macOS Feedback 조사에 공통적으로 필요하며, 사용자 Privacy를 불필요하게 침해하지 않는가?
Yes이면 Core Payload 후보가 될 수 있다.
특정 앱에서만 필요한 정보라면:
metadata
를 사용한다.
특정 Backend에서만 필요한 정보라면:
Transport / Backend
에서 처리한다.
이 경계를 유지하는 것이 SDLFeedbackKit Payload를 단순하고 장기적으로 안정적으로 유지하는 핵심 원칙이다.
